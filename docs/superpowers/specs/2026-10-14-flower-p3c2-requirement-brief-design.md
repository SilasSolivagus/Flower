# Flower P3-C2 设计：需求简报

日期：2026-10-14
上位文档：`docs/superpowers/specs/2026-09-28-flower-data-model-design.md`；P2-A 变更 PRD 设计 `2026-10-08-flower-p2a-change-prd-design.md`（文档、模板、修订、评论、覆盖需求）。本文只写 P3-C2 的范围，以及在上位文档基础上补充或改变的决定。

## 1. 背景与范围

产品经理在写 PRD 之前，要查代码仓库、取数、和研发确认可行性、和需求方确认方案。这些结论目前散在群聊和个人文档里。「需求简报」把它们按固定结构记在 Flower 里：记录的是讨论到当前为止的结论，不是会议流水账；全部小节填完、闸口通过后再写 PRD。简报同时是 P5「Agent 生成 PRD」的上下文来源。

阶段调整（2026-10-14 用户决定）：P3-C2 改为需求简报；周期汇总顺延为 P3-C3，内容为完成清单、在推进与风险、进展摘录、数字与对比。

P3-C2 包含：简报文档类型、预置简报模板、头部结构化字段、覆盖需求、软闸口、一键转 PRD 草稿、Markdown 导出与只读上下文接口。

不在 P3-C2 内：周期汇总（P3-C3）、AI 起草与改写（P5）、MCP（P4）、代码仓库直连（P6；第 8 节证据先手填）。

## 2. 用户已确认的决定（2026-10-14）

| 主题 | 决定 |
|---|---|
| 顺序 | 先做需求简报（P3-C2），周期汇总顺延为 P3-C3 |
| 形式 | 用户提供的模板（附录 A）：头部信息表 + 18 节正文；每节必填，不涉及的写「不适用：理由」 |
| 实现方式 | 方案 A：新增文档类型「简报」，复用现有文档系统（编辑器、模板与必填小节、修订、划词评论、`[[ ]]` 链接、附件） |
| 对应关系 | 一份简报可覆盖多条需求，每条需求最多挂一份简报（与变更 PRD 相同） |
| 闸口 | 软闸口：显示检查结果与未通过项，不阻止改状态和转 PRD |
| Agent 上下文 | 本期做 Markdown 复制 / 下载与只读上下文接口；MCP 在 P4 复用 |
| 设计三节 | 数据与文档模型、页面、权限接口与验证，按 2026-10-14 对话确认的内容 |

## 3. 数据与文档模型

### 3.1 文档

- `documents.kind` 增加 `brief`。简报属于产品，复用编辑器、修订、划词评论、`[[ ]]` 链接、图片附件。
- 编号：按产品单独编号，显示为 `{产品}-B-n`（如 `PAN-B-3`），`[[ ]]` 语法与链接卡支持该写法。
- 状态：讨论中（`discussing`）、可写 PRD（`ready`）、已转 PRD（`converted`）、已废弃（`discarded`）。与变更 PRD、模块文档的状态共用 `documents.status` 列，取值分别定义。

### 3.2 与需求的关系

- `requirements` 增加 `brief_document_id`（与 `change_document_id` 同样的写法）：一份简报覆盖多条需求，每条需求最多挂一份简报。
- 需求详情显示所挂简报；简报列出覆盖的需求，可添加、移除。

### 3.3 头部信息（结构化，新表 `document_briefs`，与文档一对一，带 `org_id` 并开启 RLS）

| 字段 | 说明 |
|---|---|
| `version` | 自由填写，如 v0.1；修订历史仍自动记录 |
| `requester_member_id` | 提出人，组织内在职真人成员，可空 |
| `decider_member_id` | 决策人，同上，可空 |
| `participant_tag_ids` | 参与方，组织职能标签多选（jsonb） |
| `author_member_id` | 作者，默认创建人，可改 |
| `related_links` | 关联文档，多条：`[[ ]]` 引用或外部网址加说明（jsonb） |
| `gate_checks` | 闸口人工项的勾选记录：项号、勾选人、时间（jsonb） |
| `converted_document_id` | 转出的变更 PRD，可空 |

### 3.4 预置模板

- 附录 A 的模板作为组织级预置「简报模板」：正文 18 节为必填小节，各节表格作为小节初始内容；「用法」三条作为模板说明显示在编辑器顶部。
- 组织可改，产品可覆盖（与 PRD 模板相同）。模板不预填任何人名。
- 已有组织在迁移中补齐；新组织在初始化时写入。

### 3.5 软闸口（第 17 节的 11 项）

自动检查（每次读取时计算）：

| 项 | 判定 |
|---|---|
| 1 第 1–14 节没有空白 | 每节在去掉模板原样内容后有实际内容，或写了「不适用：理由」（理由非空） |
| 7 第 8 节现状都有证据与日期 | 第 8 节表格中填了结论的每一行，「证据」与「核对日期」两列非空 |
| 10 第 16 节没有阻塞 PRD 的问题 | 第 16 节表格中「是否阻塞 PRD」列没有「是」 |

其余 8 项为人工勾选，记录勾选人与时间，可取消。结果显示在侧栏，未通过的自动项说明原因并可跳到对应小节。软闸口不阻止改状态，也不阻止转 PRD。

### 3.6 转 PRD

- 生成一份变更 PRD 草稿：按附录 A 第 18 节的对应表，把简报各节内容依次放入 PRD 模板对应章节（原样拼接，章节下注明来源小节）；PRD 覆盖与简报相同的需求（需求已挂其他 PRD 的跳过并在结果里列出）。
- 简报状态改为「已转 PRD」，记录 `converted_document_id`；PRD 顶部显示「由简报 {key} 生成」。
- 已转过的简报再转时提示已有 PRD，可打开或再生成一份新草稿（新草稿替换 `converted_document_id`）。

### 3.7 Agent 上下文

- 导出内容：头部字段、正文 Markdown、闸口结果、覆盖的需求（编号、标题、状态）、转出的 PRD。
- 简报页「复制为 Markdown」「下载 .md」；只读接口 `GET /api/v1/orgs/:org/briefs/:id/context`（`format=markdown|json`）。

## 4. 页面

- 主导航「文档」增加页签「简报」：列表列出编号、标题、状态、覆盖需求数、闸口进度（如 7/11）、决策人、更新时间；按状态、决策人筛选。
- 新建：文档页「新建简报」（产品、标题、可选覆盖需求）；需求详情侧栏「简报」区块，没有时「新建简报」并自动覆盖该需求，已有时显示标题、状态、闸口进度并可进入。
- 简报详情（沿用 PRD 页面布局）：顶部编号、标题、状态切换；正文编辑器按模板展开、表格可编辑；侧栏依次为头部信息、覆盖的需求、写 PRD 闸口（自动项结果与原因、人工勾选框与勾选人时间）、操作（转 PRD、复制为 Markdown、下载 .md）；修订、评论、被引用同 PRD 页。
- 转 PRD：弹窗先列出未通过的闸口项，确认后生成并跳转；两边互相链接。
- 1440 与 760 宽度下页面本身不横向滚动；正文宽表格在编辑器内横向滚动。

## 5. 权限、接口与事件

- 查看：能看到该产品的成员（访客仅限被授权产品）。新建、编辑正文与头部、关联需求、改状态、转 PRD、勾选闸口：产品编辑及以上。改简报模板：组织管理员（产品覆盖为产品管理员）。只读 Token 可读简报与上下文；读写 Token 只在其产品范围内写。
- 接口在 `/api/v1` 下：简报列表、头部读写、闸口结果与人工勾选、转 PRD、上下文；正文保存、修订、评论、覆盖需求复用现有文档接口。所有查询在 `withOrg` 中并按可见产品过滤。
- 事件（同一事务）：`brief.created`、`brief.updated`（头部字段 `changes`）、`brief.gate_checked`、`brief.converted`；正文保存、状态、覆盖需求沿用现有文档事件。
- 通知：被设为决策人时发「被指派」（P3-B1）；正文 @ 沿用现有逻辑。新事件不接入企业微信群推送（P3-C3 再议）。

## 6. 迁移与验证

- 迁移：`documents.kind` 增加取值、`document_briefs`（RLS）、`requirements.brief_document_id`、简报编号所需的计数；为已有组织补齐预置简报模板。不导入历史数据。
- 单元测试：闸口自动三项（空小节、「不适用：理由」、阻塞问题、证据与日期列）；转 PRD 的拼接与需求覆盖；上下文导出格式。
- 接口测试：权限（组织管理员、产品管理员、编辑、只读、访客、只读 Token、限定产品的 Token）；看不到的产品的简报不出现在列表与上下文接口。
- 端到端测试：从需求新建简报、编辑头部与正文、闸口显示与勾选、转 PRD 跳转与互链、复制与下载 Markdown；1440 与 760。
- pan123 复验：用一条真实需求按模板写一份简报并转 PRD，核对内容对应；perf 加简报列表与上下文接口，p95 低于 300 毫秒。
