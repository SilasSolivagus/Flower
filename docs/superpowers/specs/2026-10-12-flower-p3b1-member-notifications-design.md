# Flower P3-B1 设计：站内通知、@ 成员与个人通知偏好

日期：2026-10-12
上位文档：`docs/superpowers/specs/2026-09-28-flower-data-model-design.md`（§6.1 领域事件、§6.2 通知中心）；P3-A 设计 `2026-10-10-flower-p3a-notifications-design.md`。本文只写 P3-B1 的范围，以及在上位文档基础上补充或改变的决定。

## 1. 范围

P3-B 拆为两段，先做 P3-B1：
- **P3-B1（本文）**：站内通知（铃铛、通知页）、@ 成员、关注、个人通知偏好、企业微信群里 @ 到人、成员与企业微信账号的绑定（手动、批量导入、扫码）。
- **P3-B2**：基础数据看板（上位文档 §6.6 中已可计算的指标）。

不在 P3-B1 内：数据看板、浏览器推送与手机推送、飞书与钉钉、通知的 AI 摘要。

## 2. 用户已确认的决定（2026-10-12）

| 主题 | 决定 |
|---|---|
| 拆分与顺序 | P3-B1 站内通知先做，P3-B2 数据看板后做 |
| 通知类型 | 被 @、被指派、关注对象变化、等我签字、系统告警 |
| 企业微信 | 被 @、被指派等个人通知同时在企业微信群里 @ 到本人 |
| 企微身份 | 两步走：先做手动填写与批量导入企微账号（userid）；同时做扫码绑定（企业微信自建应用的网页授权），真实扫码在正式部署后验证 |
| 发到哪个群 | 每个产品指定一个「个人提醒通道」（P3-A 已登记的企微通道） |
| 偏好默认值 | 站内全开；企微只开被 @、被指派、等我签字；邮件全关。每人可改 |
| 关注口径 | 负责、被分配、评论过、被 @ 的需求与 PRD 自动关注；详情页可取消，也可手动关注其他对象 |
| 生成方式 | 方案 B：业务写入只在事件里记下新增的被 @ 成员；收件人计算与分发在 P3-A 的后台循环里异步完成 |
| 设计四节 | 数据模型、@ 与绑定、通知生成、界面，按 2026-10-12 对话确认的内容 |

## 3. 数据模型

新增租户表（均带 `org_id` 并开启 RLS，`wecom_apps` 见下文）：

- `member_notifications`（站内通知）：`member_id`、`event_id`（可空，系统告警没有对应事件）、`kind`（mentioned / assigned / followed_change / signoff_due / system_alert）、`subject_type`（requirement / document / task / schedule）、`subject_id`、`title`、`body`、`url`、`actor_member_id`（可空）、`created_at`、`read_at`。唯一约束（`member_id`, `event_id`, `kind`），`event_id` 为空时不参与唯一约束。
- `member_notification_prefs`（个人偏好）：`member_id`、`kind`、`in_app`、`wecom`、`email`，唯一（`member_id`, `kind`）。没有记录时按默认值（见 §2）。
- `subscriptions`（关注）：`member_id`、`subject_type`（requirement / document）、`subject_id`、`source`（auto / manual）、`muted_at`（取消关注时记录，不删行，避免被自动关注回来）、`created_at`；唯一（`member_id`, `subject_type`, `subject_id`）。
- `notification_cursors`（后台处理进度）：每个组织一行，记录最后处理的事件（`created_at`, `id`）与更新时间。

改动现有表：

- `members` 加 `wecom_userid`（可空，同一组织内唯一）。
- `products` 加 `personal_channel_id`（可空，指向 `notification_channels`；只能是对本产品可用、已启用的企微通道）。
- 新增租户表 `wecom_apps`（每个组织最多一行，开启 RLS）：`corp_id`、`agent_id`、`secret`（按 P3-A 的方式加密）、`secret_hint`、`bind_enabled`、`updated_at`；接口只返回脱敏提示。
- `organizations` 加 `personal_email_channel_id`（可空，指向一个邮件通道），用于个人通知的邮件。

事件补充：评论新建或修改、需求描述修改、PRD 正文保存的事件 payload 带 `mentioned_member_ids`，只含本次保存相对上一版新增的被 @ 成员。

迁移：`--replace` 清理以上新表；旧系统没有站内通知数据，不迁移。

实现补充（计划 2026-10-12）：

- 游标按领域事件的 `occurred_at`（事件表没有 `created_at`）与 `id` 比较，另记连续失败的事件与次数；只处理早于本库仍在进行中的事务开始时间的事件，避免越过未提交事务里的事件。
- 扫码绑定的一次性 `state` 存在新租户表 `wecom_bind_states`（只存摘要，10 分钟过期，开启 RLS）。
- 个人提醒写入 P3-A 发送队列时 `kind = personal`；邮件请求体可以带收件人，覆盖通道配置里的收件人。
- 事件 payload 沿用现有的驼峰命名：`mentionedMemberIds`。

## 4. @ 成员与企业微信绑定

### 4.1 @ 成员

- 写法：正文存 `[@姓名](member:成员ID)`。显示时按成员 ID 取当前姓名；成员离开组织后显示为灰色的原名。代码块与行内代码中的 `@` 不解析。
- 输入：评论、需求描述（纯文本输入框加补全弹层）与 PRD 编辑器（BlockNote 内联元素）中输入 `@` 弹出成员搜索，按姓名或邮箱匹配；上下选择、回车插入、Esc 关闭，与 `[[` 补全一致。
- 显示：成员标签；悬停显示邮箱与是否已绑定企业微信。
- 权限：看不到该产品的成员在补全里标「看不到这个产品」，可以插入，但不给他发通知。@ 自己不发通知。
- 新增比对：每次保存与上一版比较，只有新出现的 @ 写入事件。

### 4.2 企业微信账号

- 手动：组织设置 → 成员，「企业微信账号」一列可编辑；同一组织内重复时报「该企业微信账号已绑定到 {姓名}」。
- 批量导入：上传 CSV（邮箱, 企业微信账号），先预览（可匹配、找不到成员、账号重复），确认后写入。
- 扫码绑定：组织管理员在组织设置 → 推送 →「企业微信应用」填写企业 ID、应用 ID、应用密钥并开启扫码绑定，页面显示需要填到自建应用「授权回调域」的地址。成员在个人设置点「绑定企业微信」，跳转到企业微信扫码登录页；回调时校验一次性 `state`，服务端用临时码向企业微信换取 userid 并保存。服务端只访问 `qyapi.weixin.qq.com`。成员可以自行解除绑定。
- 验证：本地用模拟的企业微信接口跑通扫码流程；真实扫码在正式部署、配置备案域名后验证。

### 4.3 企业微信群里 @ 到人

个人提醒发到所属产品的「个人提醒通道」，消息为 markdown，正文用 `<@userid>` @ 到本人。成员没有绑定企微账号、产品没有指定个人提醒通道、或该通道停用时，不发企微，只保留站内通知。

## 5. 通知生成与分发

### 5.1 处理流程

- 在 P3-A 的后台循环中按组织处理：以 `SKIP LOCKED` 锁定该组织的游标，按（`created_at`, `id`）顺序读取游标之后的新事件，每轮最多 500 条。只处理日常操作产生的事件，`legacy.*` 事件不处理。
- 每条事件在独立的子事务中处理（计算收件人、写站内通知、补自动关注、写待发记录），成功后前移游标。同一条事件连续失败 3 次后跳过并记录警告。
- 上线时游标初始化为当前最新事件，不为历史事件补发通知。

### 5.2 收件人规则

操作人本人不通知；看不到该产品的人不通知；同一事件同一人只发一条，按「被 @ > 被指派 > 关注对象变化」取最高的一种。

| 类型 | 触发 | 收件人 |
|---|---|---|
| 被 @ | 评论、需求描述、PRD 正文中新增的 @ | 被 @ 的成员 |
| 被指派 | 需求负责人变更、新增分配、任务指派、PRD 负责人变更 | 新的负责人或被分配的成员 |
| 关注对象变化 | 需求状态变化、优先级与迭代变化、新评论、PRD 状态变化 | 关注者（未取消关注） |
| 等我签字 | 检查项进入待签字 | 对应分配的成员；没有分配时为该职能标签的成员（与工作台口径一致） |
| 系统告警 | 定时推送进入告警状态（后台循环在写告警时直接生成） | 组织管理员 |

自动关注：处理事件时为负责人、被分配者、评论者、被 @ 者补上关注；已取消关注的不再加回。

### 5.3 按偏好分发

- 站内：写 `member_notifications`。
- 企业微信：同一轮内同一产品的个人提醒合并为一条 markdown（每条一行，如 `<@userid> 被 张三 @ 了：[PAN-12 标题](链接)`），超过 4096 字节分条；走 P3-A 的发送队列（限流、重试、发送记录），来源标「个人提醒」。
- 邮件：发到组织指定的个人通知邮件通道，收件地址为成员邮箱；同一轮内同一人的多条合并为一封。未指定邮件通道时不发邮件。

### 5.4 已读与清理

打开对应的需求、PRD 或任务时，相关的本人通知标为已读；铃铛面板提供「全部标为已读」。已读超过 90 天的通知由后台循环删除。

## 6. 界面

- **顶栏铃铛**：显示未读数（每 30 秒刷新）。面板列出最近 20 条，按「今天 / 更早」分组，可切换「全部 / 未读 / @我」；每条为「谁对什么做了什么」与相对时间，未读有圆点；点击跳转并标为已读；底部「全部标为已读」「查看全部」。
- **通知页** `/[org]/notifications`：按类型、已读状态筛选，分页。
- **个人设置**：通知偏好表（行为五类通知，列为站内、企业微信、邮件；企微列在未绑定或产品未指定个人提醒通道时置灰并说明原因；系统告警一行只对组织管理员显示）；企业微信绑定状态、扫码绑定与解除绑定。
- **组织设置**：成员页加「企业微信账号」列与批量导入；推送页加「企业微信应用」页签（企业 ID、应用 ID、应用密钥、允许扫码绑定、回调地址）与「个人通知邮件通道」选择。
- **产品设置 → 推送**：顶部加「个人提醒通道」选择。
- **需求与 PRD 详情**：「关注 / 已关注」按钮，悬停说明关注原因。
- **工作台**：不改。工作台是待办，铃铛是动态；「等我签字」在两处口径一致。

## 7. 验证

- 单元测试：@ 解析与新增比对；收件人规则与去重；偏好默认值；游标只处理一次（并发两实例）；失败重试与跳过；企微合并与分条；扫码绑定回调（模拟企业微信接口，含 `state` 校验失败、账号重复）；批量导入预览。
- 接口测试：权限（本人、组织管理员、产品管理员、只读、只读 Token）；应用密钥不出现在任何响应里；看不到产品的成员收不到通知。
- 端到端测试：@ 补全并收到站内通知、被指派、关注与取消关注、偏好开关、铃铛面板与通知页、成员企微账号与批量导入；1440 与 760 两种宽度。
- 测试群联调：在 pan123 上给测试成员手动填写企微账号，验证群里 @ 到人的显示（每次发送前征得用户确认）。
