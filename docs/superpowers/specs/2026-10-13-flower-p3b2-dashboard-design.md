# Flower P3-B2 设计：基础数据看板

日期：2026-10-13
上位文档：`docs/superpowers/specs/2026-09-28-flower-data-model-design.md`（§6.6 管理员数据看板、§8 分阶段）。本文只写 P3-B2 的范围，以及在上位文档基础上补充或改变的决定。

## 1. 范围

- 产品看板：按产品查看需求流速、前置时间、流动时间、在制品、版本按期达成率、迭代承诺完成率、专项完成率、评审效率与驳回率。
- 组织汇总页：组织管理员按产品对比关键指标。
- 看板接口（只读）。

不在 P3-B2 内：每日快照表、物化视图、看板导出与订阅推送、§7「产品工作情况表」所需的新字段与视图（待讨论）、P6 的管理员看板完善。

## 2. 用户已确认的决定（2026-10-13）

| 主题 | 决定 |
|---|---|
| 给谁看 | 产品视角为主（产品看板），另加组织汇总页 |
| 历史缺数 | 历史版本没有基线日期时，用所属迭代的结束日代替并注明口径；迭代承诺完成率只统计在 Flower 里开始、有承诺范围快照的迭代，没有时显示「暂无数据」 |
| 时间范围 | 按时间段（默认近 90 天，可选 30 天、180 天、自定义，趋势按周）与按迭代两种方式 |
| 计算方式 | 方案 A：打开看板时实时计算，前端缓存；不建快照表。数据量增大后再加每日快照，不影响现有结构 |
| 设计三节 | 指标口径、页面、权限与验证，按 2026-10-13 对话确认的内容 |

数据现状（2026-10-13 只读核实，pan123）：状态流转 3311 条（2026-03 起）；发布版本 14 个、已发布 10 个，计划日期与基线日期均为空；迭代承诺范围快照 0 条；检查项结果 795 条、签字 287 条；专项 2 个。

## 3. 指标口径

状态按流程中的状态类别归类：backlog（待规划）、unstarted（未开始）、started（进行中）、completed（已完成）、canceled（已取消）。「进入某类」以 `state_transitions` 为准。通用规则：已删除的需求不计；「已取消」不算完成，也不进入分母；时间段与周按组织时区划分，周从周一开始。

| 指标 | 口径 |
|---|---|
| 吞吐量（流速） | 时间段内每周进入 completed 的需求数（周趋势）；同一需求反复进出时按最后一次进入计 |
| 前置时间 | 需求创建到进入 completed 的天数；显示中位数与 85 分位 |
| 流动时间 | 需求第一次进入 started 到进入 completed 的天数；显示中位数与 85 分位 |
| 在制品 | 每周末处于 started 的需求数（周趋势，由流转记录推算）；当前按具体状态拆分的数量与每个状态的平均停留天数 |
| 版本按期达成率 | 时间段内已发布版本中，发布日不晚于基线日期的比例；没有基线日期的版本用所属迭代的结束日代替，并标「按迭代结束日计」；另列逾期天数，以及已过计划日期仍未发布的版本 |
| 迭代承诺完成率 | 只计有承诺范围快照的迭代：快照内需求在迭代结束时（进行中的迭代计到现在）进入 completed 的比例；同时列出中途加入、移出的需求数 |
| 专项完成率 | 每个专项内 completed 数 ÷（总数 − canceled 数） |
| 评审效率 | 检查项从开始评审到通过的天数中位数，按检查项分别列出 |
| 驳回率 | 时间段内出现过「驳回」的检查项 ÷ 有结论的检查项；取自领域事件，先驳回后通过的检查项计为驳回过 |

评审效率与驳回率依赖领域事件，迁移来的旧事件只覆盖部分检查项变化，页面注明统计起点。

## 4. 页面

### 4.1 产品看板

顶部导航加「看板」，路径 `/{org}/dashboard?product=…`，可切换产品。自上而下：

1. 筛选栏：时间段（近 30 / 90 / 180 天、自定义）与「按迭代」切换。
2. 关键数字卡片：吞吐量（周均）、前置时间中位数、流动时间中位数、当前在制品、版本按期达成率、驳回率；每张卡片标出与上一个同长度时间段相比的升降。
3. 趋势：每周吞吐量、在制品周趋势、前置时间与流动时间的 85 分位走势。
4. 卡在哪儿：当前各状态的需求数与平均停留天数（按停留天数降序）；停留最久的前 10 条需求，点击进入需求详情。
5. 迭代与版本：每个迭代一行（承诺完成率、中途加入与移出数）；每个版本一行（计划日、实际发布日、是否按期；用迭代结束日代替的行带标注）。
6. 专项：每个专项的完成率进度条。
7. 评审：各检查项的评审天数中位数与驳回率。

### 4.2 组织汇总页

组织设置里加「看板」，每个产品一行，列出 §4.1 第 2 步的关键数字，点击产品名进入产品看板。

### 4.3 通用

- 每个指标旁有「?」，悬停显示 §3 的口径。
- 数据不足时显示「暂无数据」并说明原因（如「还没有在 Flower 里开始的迭代」）。
- 图表沿用项目现有样式；1440 与 760 两种宽度下页面不横向滚动。

## 5. 权限与接口

- 产品看板：能看到该产品的成员都可以查看（含编辑、只读成员；访客仅限被授权的产品）。
- 组织汇总页：仅组织管理员。
- 接口在 `/api/v1` 下，只读；只读 API Token 可调用。
- 所有查询在 `withOrg` 中进行，并按当前用户可见的产品过滤；不新增租户表，不新增迁移。

## 6. 验证

- 单元测试：用构造的需求与流转记录校对每个指标，覆盖反复进出 completed、已取消与已删除的需求、跨周与跨时区边界（组织时区、周一开始）、在制品周趋势推算、版本缺基线日期时用迭代结束日、无快照迭代显示「暂无数据」、先驳回后通过计为驳回过。
- 接口测试：权限（组织管理员、产品管理员、编辑、只读、访客、只读 Token）；看不到的产品的数据不出现在任何响应里，包括组织汇总。
- 端到端测试：产品看板与组织汇总页的显示、筛选与按迭代切换、「暂无数据」与口径说明、从停留最久的需求进入详情；1440 与 760 两种宽度。
- 性能：用现有的真实数据性能测量命令在 pan123 上测量看板接口，每个接口在 300 毫秒内返回。
- 真实数据核对：在 pan123 上挑选几项（某周吞吐量、某个版本是否按期、某个专项完成率）用 SQL 手工计算对照。

## 7. 待讨论：产品工作情况表

用户提供了一张正在使用的企业微信智能表「产品工作情况管理表」，要求先记录其需求，之后讨论在 Flower 中如何实现。不在 P3-B2 范围内。

用途：跟踪每位产品经理手上在推进的需求与任务，看清每一条处在哪个阶段、停留多久、卡在哪里、下一步由谁跟进。

| 表中的列或视图 | Flower 现状 |
|---|---|
| 需求/任务名称、负责 PM、类型、优先级 | 已有（需求字段） |
| 当前阶段、进入当前阶段日期、本阶段停留天数、在制时长 | 可由状态与 `state_transitions` 计算，未单独展示 |
| 启动日期 | 可计算（第一次进入 started） |
| 实际上线日期 | 可由流转记录或版本发布时间得到 |
| 预计上线/完成日期 | 需求上没有该字段 |
| 阻塞/风险 | 需求上没有专门字段（迭代有阻塞项） |
| 下一步 & 跟进人 | 没有 |
| 视图：任务老化、按阶段看板、按 PM 盯在手 | 没有对应页面（工作台只列「我负责的」） |

初步判断：老化与停留天数部分可复用本看板的计算；预计上线日期、阻塞/风险、下一步与跟进人需要为需求新增字段，并配套视图。具体方案待讨论。
