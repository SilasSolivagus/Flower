# Flower P3-C1 设计：工作跟进（替代「产品工作情况表」）

日期：2026-10-13
上位文档：`docs/superpowers/specs/2026-09-28-flower-data-model-design.md`；P3-B2 设计 `2026-10-13-flower-p3b2-dashboard-design.md` §7（产品工作情况表，待讨论）。本文只写 P3-C1 的范围，以及在上位文档基础上补充或改变的决定。

## 1. 背景与范围

用户团队用一张企业微信智能表「产品工作情况管理表」跟进每位产品经理手上在推进的工作：每日站会逐条说进展，每周周会总结，月度、季度、半年、年度形成部门工作汇总。表的列：需求/任务名称、负责 PM、类型、当前阶段、本阶段停留（天）、优先级、启动日期、进入当前阶段、阻塞/风险、下一步 & 跟进人、预计上线/完成、实际上线日期、在制时长；视图：全部记录、任务老化、按阶段看板、按 PM 盯在手。

拆分：

- **P3-C1（本文）**：跟进。需求的类型与预计上线日期、暂停、进展记录、工作项、跟进视图、工作台与组织设置。
- **P3-C2**：周期汇总。汇总页（周、月、季、半年、年；按产品经理、类型、产品）、导出 Markdown 与 Excel、定时推送到群；P3-A 的推送规则接入本文的新事件。
- **P5**：AI 生成总结初稿（依赖组织级 AI key 与内置 AI 能力）。

不在 P3-C1 内：周期汇总、导出与推送、AI 总结、智能表历史条目导入（以后需要时做 CSV 导入）、工作项的评论与 `[[ ]]` 链接、看板上拖动卡片改状态。

## 2. 用户已确认的决定（2026-10-13）

| 主题 | 决定 |
|---|---|
| 非需求工作 | 技术支持、协调对接等建为单独的「工作项」，不占需求编号，不进入需求流速指标 |
| 暂停 | 暂停标记 + 原因，状态保持不变；暂停期间不计老化、不计在制，恢复后接着算 |
| 阻塞/风险 | 复用需求上已有的阻塞项；工作项也挂阻塞项 |
| 下一步 & 跟进人 | 按条保存进展记录（进展、下一步、跟进人），列表显示最新一条 |
| 跟进范围 | 需求进入设计阶段及之后（未开始、进行中类别）自动加入跟进；收集阶段由产品经理手动加入；上线或取消后不再显示为在手，但保留供汇总 |
| 工作项归属 | 建在组织下，可选关联一个产品；编号按组织 `W-n` |
| 老化 | 两档阈值，组织可改：本阶段停留（扣除暂停）超过 14 天标黄、超过 30 天标红；另列超过 7 天没有进展记录的条目 |
| 历史数据 | 智能表条目不在本期导入，上线后手工建；以后需要时再做导入 |
| 实现方案 | 方案 A：字段放在所属对象上（需求加列、新建工作项表），进展记录与阻塞项由需求和工作项共用 |
| 设计三节 | 数据模型、页面与视图、权限与验证，按 2026-10-13 对话确认的内容 |

智能表的列与 Flower 的对应：

| 智能表 | Flower |
|---|---|
| 需求/任务名称、负责 PM、优先级 | 需求标题、负责人、优先级字段；工作项标题、负责人 |
| 类型（新功能、体验优化、线上问题、技术支持、协调对接） | 需求新增内置字段「类型」（新功能、体验优化、线上问题）；工作项内置字段「工作类型」（技术支持、协调对接）；选项均可在字段字典修改 |
| 当前阶段（收集中、设计中、待开发、评审排期、开发中、测试验收、已上线、已暂停） | 需求的流程状态（PAN：收集 / 待评估 / 已评估、待设计 / 设计中、待开发、开发中、测试中、已上线）；「评审排期」如需要由组织管理员在流程模板中自行增加状态；「已暂停」为暂停标记；工作项为进行中 / 已完成 / 已取消 |
| 本阶段停留、进入当前阶段、在制时长、启动日期 | 由状态流转与暂停事件计算；工作项的启动日期为字段 |
| 阻塞/风险 | 阻塞项 |
| 下一步 & 跟进人 | 最新一条进展记录 |
| 预计上线/完成 | 需求 `expected_date`、工作项 `expected_date` |
| 实际上线日期 | 需求最后一次进入完成类的日期；工作项完成时间 |

数据现状（2026-10-13 只读核实，pan123）：PAN 处于未开始、进行中类别的需求 81 条（待设计 27、待开发 14、设计中 23、开发中 14、测试中 3）；阻塞项 9 条（进行中 4）。

## 3. 数据模型

### 3.1 需求（`requirements` 新增列）

| 列 | 说明 |
|---|---|
| `tracked_since` timestamptz | 加入跟进的时间。状态第一次进入未开始或进行中类别时自动填写（已有值或曾被手动移出时不再自动填写）；收集阶段可手动加入；手动移出时清空；上线或取消后保留 |
| `tracking_opted_out` boolean，默认 false | 手动移出后置为 true，阻止再次自动加入；手动加入时置回 false |
| `expected_date` date | 预计上线日期 |
| `paused_at` timestamptz、`pause_reason` text | 暂停中时非空；恢复时清空 |

「跟进中」= `tracked_since` 非空且当前状态不在已完成、已取消类别。

「类型」是新增的内置单选字段（`key = type`，作用于需求），组织预置选项：新功能、体验优化、线上问题。已有组织在迁移中补齐。

### 3.2 工作项（新表 `work_items`）

| 列 | 说明 |
|---|---|
| `id`、`org_id` | |
| `product_id` | 可空；关联产品 |
| `number` | 组织内连续编号，显示为 `W-n`；`organizations` 新增 `work_item_seq` 计数列 |
| `title`、`description` | 描述为 Markdown，沿用需求描述的输入框与 @ |
| `owner_member_id` | 负责人，须为组织内在职的人类成员 |
| `status` | `active` / `done` / `canceled` |
| `started_on`、`expected_date` | 启动日期、预计完成日期 |
| `done_at` | 进入 `done` 的时间 |
| `paused_at`、`pause_reason` | 同需求 |
| `created_by`、`created_at`、`updated_at`、`deleted_at` | 软删除 |

「工作类型」是新增的内置单选字段（`key = work_type`，`applies_to = work_item`），预置选项：技术支持、协调对接；值存在现有的字段值表中（`field_values` 增加对工作项的引用，规则同进展记录的「只挂一个对象」）。

### 3.3 进展记录（新表 `progress_updates`）

| 列 | 说明 |
|---|---|
| `id`、`org_id` | |
| `requirement_id`、`work_item_id` | 二者恰有一个非空（检查约束） |
| `body` | 进展 |
| `next_step` | 下一步，可空 |
| `follower_member_id` | 跟进人，可空；须为组织内在职的人类成员 |
| `author_member_id`、`created_at`、`edited_at`、`deleted_at` | 软删除 |

### 3.4 阻塞项（`blockers` 修改）

新增 `work_item_id`；`requirement_id` 改为可空；检查约束要求二者恰有一个非空。

### 3.5 组织设置

`organizations.settings.tracking`：`{ warnDays: 14, alertDays: 30, staleUpdateDays: 7 }`，缺省时取这三个默认值。

### 3.6 迁移

- 一个迁移完成上述列、表、约束；`work_items`、`progress_updates` 开启 RLS（参照 `0002_rls.sql`）。
- 回填：当前处于未开始、进行中类别的未删除需求，`tracked_since` 取最近一次进入该类别的流转时间（没有流转记录时取 `state_changed_at`）。
- 补齐内置字段「类型」「工作类型」与预置选项。

### 3.7 停留与老化的计算

- 本阶段停留天数 = 进入当前状态（工作项为启动日期，没有时取创建时间）至今，扣除其中的暂停区间；暂停区间来自暂停、恢复事件，正在暂停时截止到暂停开始。
- 在制时长 = 加入跟进（工作项为启动日期）至今或至完成，同样扣除暂停区间。
- 老化：停留超过 `warnDays` 为黄、超过 `alertDays` 为红；暂停中的条目不标色。
- 无进展：最新一条进展记录（没有时取加入跟进的时间）早于 `staleUpdateDays` 天；暂停中的条目不计。
- 天数按组织时区计算。

### 3.8 通知（复用 P3-B1）

- 工作项设置或更换负责人：负责人收到「被指派」，并自动关注。
- 进展记录指定跟进人：跟进人收到「被指派」，原因为「你是下一步跟进人」。
- 关注了需求或工作项的人，在新增进展记录时收到「关注对象变化」。

## 4. 页面与视图

### 4.1 主导航「跟进」（`/{org}/tracking`）

跨产品显示当前用户可见的需求与工作项。筛选：产品、负责人、类型、只看暂停、只看有阻塞；筛选与页签写入地址栏。右上角「新建工作项」。

1. **全部在手**：每条一行。列：编号、标题、负责人、类型、当前阶段（暂停时加「已暂停」标签）、本阶段停留、优先级、启动日期、进入当前阶段、阻塞/风险（进行中的条数与第一条）、最新进展 · 下一步 · 跟进人、预计上线、实际上线、在制时长。默认只显示跟进中的条目，可切换为同时显示最近 30 天内完成的。
2. **任务老化**：按本阶段停留天数降序，超过阈值标黄或标红；下方单列超过阈值天数没有进展记录的条目。
3. **按阶段看板**：选定单个产品时按该产品流程状态分列，选「全部产品」时按状态类别（未开始、进行中）分列；工作项单独一列「工作项」。卡片显示标题、负责人、停留天数、阻塞标记；只读，不能拖动。
4. **按产品经理**：按负责人分组，组标题显示条数、暂停数、阻塞数、老化数；站会时按人逐个过。

每行与每张卡片有「写进展」：小窗填写进展、下一步、跟进人，可顺手修改预计日期；连续填写时保留上一次选择的跟进人。

### 4.2 需求详情

- 侧栏「跟进」区块：加入 / 移出跟进、预计上线日期、暂停（填原因）/ 恢复。
- 正文新增「进展记录」页签：时间倒序，可新增；作者本人可修改、删除。
- 阻塞项位置与用法不变。

### 4.3 工作项

- 新建：标题、工作类型、负责人、可选产品、启动日期、预计完成日期。
- 详情页 `/{org}/work-items/W-n`：基本信息、状态切换（进行中、已完成、已取消）、暂停 / 恢复、进展记录、阻塞项、关注按钮。

### 4.4 工作台

- 「我负责的」加入我负责的进行中工作项。
- 新增「等我跟进」：我是最新一条进展记录跟进人、且仍在跟进中的条目。

### 4.5 组织设置「跟进」

三个阈值，组织管理员可改。

### 4.6 通用

1440 与 760 两种宽度下页面本身不横向滚动；表格在容器内横向滚动，标题列固定。

## 5. 权限与接口

- 需求的跟进设置、暂停、进展记录：该产品编辑及以上；只读与访客只能查看。
- 关联产品的工作项：同需求，按该产品角色。
- 不关联产品的工作项：组织非访客成员可查看与新建；修改限负责人、创建人与组织管理员；访客不可见。
- 进展记录：作者本人可修改、删除；产品管理员（不关联产品时为组织管理员）可删除。
- API Token：只读 Token 只读；读写 Token 只在其产品范围内写；不关联产品的工作项要求全部产品范围的 Token。
- 老化阈值：组织管理员。
- 所有查询在 `withOrg` 中进行并按可见产品过滤；看不到的产品的需求与工作项不出现在任何响应里，包括分组计数。
- 接口在 `/api/v1` 下：跟进列表（参数选择视图与筛选）、需求跟进设置与进展记录、工作项增删改查与状态、暂停、进展记录、阻塞项、组织跟进设置。
- 领域事件（同一事务内 `recordEvent`）：需求加入 / 移出跟进、预计日期变化、暂停、恢复；工作项新建、修改、状态变化、暂停、恢复、删除；进展记录新建、修改、删除；阻塞项沿用现有事件并覆盖工作项。

## 6. 验证

- 单元测试：停留扣除暂停（跨时区、暂停跨状态变化、多次暂停）；自动加入跟进（第一次进入未开始或进行中时加入、手动移出后不再自动加入）；老化分档与无进展判定；进展记录与阻塞项「恰有一个对象」的约束。
- 接口测试：权限（组织管理员、产品管理员、编辑、只读、访客、只读 Token、限定产品的 Token）；看不到的产品的数据不出现在任何响应与计数里。
- 端到端测试：四个页签与筛选、写进展、暂停与恢复、工作项全流程、需求详情跟进区块、工作台「等我跟进」；1440 与 760。
- 迁移核对（pan123）：新表 RLS；回填 `tracked_since` 的需求数与 SQL 一致（预期 81）；需求数量不变。
- 性能：`perf` 加入跟进列表四个视图，p95 低于 300 毫秒。
- 界面复验：pan123 上两个账号复验写进展与跟进人通知。
